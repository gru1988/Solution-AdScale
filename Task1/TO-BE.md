## 1. Выбор архитектурного стиля

### 1.1. Рассмотренные варианты

| Критерий | Оставить монолит (оптимизировать) | Сразу переписать на микросервисы | Модульный монолит | **Strangler Fig (постепенная декомпозиция)** |
|---|---|---|---|---|
| Укладываемся в 3 месяца | да, но цель не достигается | **нет**: 6–12+ мес. до первого результата | частично | **да**: первый выделенный сервис за 6–8 недель |
| Снимает БД с hot path | частично (кеш внутри монолита) | да | частично | **да** |
| Независимое масштабирование аукциона | **нет** | да | нет (один деплой) | **да** для выделенных частей |
| Изоляция отказов | нет | да | частично | **да** для выделенных частей |
| Риск для непрерывности бизнеса | низкий | **очень высокий** (Big Bang) | низкий | **низкий**: переключение по одному маршруту, откат через роутинг |
| Нагрузка на команду 35 чел. без SRE | низкая | **неподъёмная** | низкая | умеренная, растёт постепенно |
| Готовность к 50 000 RPS и мультирегиону | нет | да | нет | **да**, к концу года |

### 1.2. Почему не оставить монолит

- Ad Server и Auction Engine нельзя масштабировать отдельно: при росте трафика придётся множить весь монолит, включая UI, финансы и аналитику, а главное — все копии всё равно упираются в **одну PostgreSQL**.
- Общий процесс и общая БД не дают изолировать отказы: тяжёлый отчёт или всплеск кликов продолжат ронять P95 аукциона.
- Ручной деплой монолита — каждый релиз рискует hot path, а штрафы DSP делают это неприемлемым.
- Даже после оптимизации запросов и добавления кеша рост до 50 000 RPS и мультирегиональность в монолите с одной БД недостижимы.

### 1.3. Почему не переписать сразу на микросервисы

- **Срок и бюджет**: полное переписывание гибридного монолита на 4 языках без документации займёт больше года, а интеграция нужна через 3 месяца.
- **Риск Big Bang**: новая система принимает весь трафик сразу, при этом в ней нет накопленных исправлений старой; откат сложен.
- **Операционная зрелость**: без контейнеризации, CI/CD, наблюдаемости и SRE команда не сможет эксплуатировать десятки сервисов (распределённые транзакции, трассировка, инциденты).
- **Неизвестные границы**: без документации и трассировки границы сервисов на старте будут выбраны неверно, получится «распределённый монолит».

### 1.4. Выбранный подход

**Strangler Fig как основная стратегия + модульный монолит для остатка.**

1. Перед монолитом ставится **Edge Gateway** — точка, через которую трафик постепенно переключается на новые сервисы (по партнёру, по проценту, по маршруту).
2. Выносятся сначала те контексты, которые **снимают главный риск**: Bidding (latency) и запись событий (нагрузка на БД). Порядок выноса определяется ценностью и связностью.
3. Остаток монолита (кабинет, финансы, аналитика на первом этапе) **разделяется на модули** с явными интерфейсами и собственными схемами в БД — это подготовка к последующему выносу и снижение связности по данным.
4. Синхронизация данных между монолитом и новыми сервисами — через **Transactional Outbox/CDC (Debezium) → Kafka**, а не через общий доступ к таблицам.

Подробное обоснование: [ADR-001](adr/ADR-001-evolution-strategy.md), порядок выноса: [ADR-002](adr/ADR-002-bidding-service-first.md).

## 2. Промежуточное решение (через 3 месяца)

### 2.1. Цель

Подключить новую DSP без деградации SLA: **≥ 18 000 RPS** (проверено нагрузочным тестом на 25 000 RPS), **P95 ≤ 80 мс** для нового DSP и ≤ 100 мс для остальных, стабильный сервис ставок, масштабируемые нагруженные компоненты, разделённые критичные и некритичные потоки.

### 2.2. Что меняем

| # | Изменение | Какую проблему закрывает (см. AS-IS) | Эффект |
|---|---|---|---|
| T1 | **Edge RTB Gateway (Envoy)** перед hot path: TLS, аутентификация DSP, rate limiting, тайм-ауты, circuit breaker, маршрутизация старый/новый | F6, B6 | Защита от перегрузки; возможность canary и отката |
| T2 | **Bidding Service** — Ad Server + Auction Engine вынесены в отдельный stateless-сервис (переиспользуется код C++/Go), контейнеризован, масштабируется горизонтально | B2, B6, F2 | Нет обращений к PostgreSQL на hot path; масштабирование независимо от монолита |
| T3 | **Снапшот кампаний в памяти** Bidding Service + **Redis** для бюджетов, pacing и частотных ограничений; обновление через CDC (Debezium) → Kafka `campaign.changes` | B1, B2, B5 | −40–60 мс на запрос |
| T4 | **Kafka** для событий (лог аукционов, win, показы, клики); Statistics Service становится консьюмером с batch-записью | B3 | Запись ушла из hot path; нагрузка на PostgreSQL по записи падает на порядки |
| T5 | **Event Collector** — лёгкий сервис приёма win/impression/click (пиксели, редиректы), только публикует в Kafka | B3, B7 | Delivery/Statistics больше не пишут в БД синхронно |
| T6 | **ClickHouse** для сырых событий и агрегатов статистики | B3, B4 | Аналитическая нагрузка уходит из PostgreSQL |
| T7 | **PostgreSQL HA (Patroni + 2 реплики) + PgBouncer**, аналитика монолита — на read replica | F1, B4, F5 | Нет SPOF; аналитика не блокирует OLTP |
| T8 | **Наблюдаемость**: OpenTelemetry, Prometheus, Grafana, Loki; SLO-дашборды по партнёрам | AS-IS п.5.4 | Видим P95 по шагам; доказываем SLA |
| T9 | **Docker + CI/CD (GitLab CI/GitHub Actions)** для новых сервисов, Kubernetes (managed) для hot path | F4 | Автоскейлинг, canary, быстрый откат |

Монолит остаётся владельцем кампаний, финансов, кабинета и аналитики, но:
- финансовый модуль получает оплачиваемые события из Kafka (агрегированно, батчами), а не из таблиц статистики;
- аналитика работает с read replica и ClickHouse;
- все модули ходят в БД через PgBouncer с отдельными пулами (bulkhead).

### 2.3. Бюджет времени отклика после изменений

| Шаг | P95, мс |
|---|---|
| Edge Gateway (TLS-терминация, аутентификация, rate limit) | 2–3 |
| Парсинг OpenRTB, валидация | 1–2 |
| Профиль пользователя и frequency caps (Redis) | 2–4 |
| Подбор кандидатов по индексу в памяти | 3–8 |
| Проверка бюджета (локальный лимит, lease из Redis — асинхронно) | < 1 |
| Аукцион и бизнес-правила | 3–8 |
| Формирование ответа (adm из предрендеренного шаблона) | 1–2 |
| Публикация событий в Kafka | 0 (асинхронно) |
| **Итого внутри AdScale** | **≈ 15–30** |
| Сеть до DSP и обратно | 10–25 |
| **Итого для DSP** | **≈ 30–55 мс** при требовании ≤ 80 мс |

Жёсткий внутренний дедлайн — **70 мс** от входа в Gateway: если не успели, возвращаем no-bid (HTTP 204), а не опоздавший ответ.

| Недели | Этап | Результат |
|---|---|---|

| 9–10 | Shadow traffic: копия продового трафика идёт в новый сервис, ответы сравниваются со старым | Подтверждена корректность аукциона |

## 3. Целевая архитектура (через год)

### 3.1. Принципы

1. **Hot path не зависит от реляционных БД и некритичных сервисов** — только память процесса, Redis и асинхронная публикация в Kafka.
2. **Event-driven по умолчанию**: сервисы обмениваются фактами (событиями) через Kafka; синхронные вызовы — только там, где нужен ответ здесь и сейчас.
3. **Database per Service**: у каждого сервиса своё хранилище, выбранное под его профиль нагрузки; чужие данные — через API или события.
4. **Bulkhead и graceful degradation**: отказ любого некритичного сервиса не влияет на аукцион.
5. **Stateless-сервисы + горизонтальное масштабирование** (Kubernetes HPA по RPS/CPU/latency).
6. **Мультирегион**: RTB active-active в двух регионах; управляющие и финансовые данные — primary в одном регионе с репликой в другом.

### 3.2. Сервисы и обоснование границ

| Сервис | Ответственность | Язык | Хранилище | Почему отдельный сервис (граница) |
|---|---|---|---|---|
| **Edge RTB Gateway** | Вход для DSP: mTLS/ключи, rate limiting, маршрутизация, тайм-ауты, circuit breaking, метрики по партнёрам | Envoy | конфигурация в Git | Инфраструктурная граница; масштабируется вместе с трафиком RTB |
| **API Gateway** | Вход для кабинета и публичного API: JWT/OAuth2, лимиты, маршрутизация к BFF | Envoy | — | Другие требования к безопасности и нагрузке, чем у RTB |
| **Bidding Service** | Приём bid request, подбор кандидатов, аукцион, формирование bid response | C++ (ядро), Go (обвязка) | память процесса + Redis | Самые жёсткие требования к latency и масштабированию; отдельный цикл релизов. Ad Server и Auction Engine объединены: один ограниченный контекст «решение о ставке», общий профиль масштабирования, лишний сетевой переход стоил бы 1–3 мс и ещё одну точку отказа |
| **Budget & Pacing Service** | Выдача порций бюджета (lease) инстансам Bidding, учёт фактического расхода, pacing | Go | Redis Cluster (+ снапшоты в PostgreSQL) | Глобальная координация расхода между сотнями инстансов; иной профиль данных (счётчики) |
| **User Profile Service** | Сегменты пользователей, frequency capping, обогащение профиля по событиям | Go | Redis Cluster / Aerospike | Большой объём key-value данных (десятки млн профилей), своя логика обновления |
| **Campaign Service** | Кампании, креативы, таргетинг, ставки, расписания; публикует изменения | Go | PostgreSQL | Источник истины для конфигурации рекламы; транзакционный CRUD |
| **Creative Delivery** | Хранение и раздача креативов, предрендер HTML/JS-шаблонов (бывший Delivery Service) | Node.js | S3 + CDN | Статика и шаблоны не должны жить в hot path; раздача через CDN |
| **Event Collector** | Приём win/billing notice, показов, кликов; валидация, дедупликация на входе, публикация в Kafka | Go | — (Kafka) | Высокий входящий поток, простая логика, отдельное масштабирование |
| **Statistics Service** | Потоковая обработка: дедупликация, антифрод-фильтры, агрегаты по минутам, реалтайм-счётчики | Go/Python (Kafka consumers) | ClickHouse + Redis | Write-heavy поток с eventual consistency |
| **Analytics Service** | Отчёты, произвольные срезы, отчётность для DSP | Python | ClickHouse (read-кластер) | Тяжёлые read-запросы изолированы от всех OLTP |
| **Finance Service** | Леджер (двойная запись), списания, счета, сверка, пополнения | Go | PostgreSQL (выделенная, sync-репликация) | Строгая консистентность и аудит; отдельная зона безопасности |
| **Payment Adapter** | Интеграция с платёжными шлюзами, обработка webhook'ов | Go | PostgreSQL Finance (своя схема) | Изоляция внешней зависимости и PCI-периметра |
| **Advertiser BFF + Dashboard** | UI рекламодателя и backend-for-frontend, агрегирует данные из Campaign, Finance, Analytics | Node.js / JS | — | Слой представления, без собственных бизнес-данных |
| **Partner Config Service** | Реестр DSP/SSP-партнёров: эндпоинты, квоты, форматы, тайм-ауты | Go | PostgreSQL (схема Campaign-кластера) | Мультиплатформенная интеграция «конфигурацией» (BG-4) |
| **Остаток монолита** | Редкие административные функции, постепенно выводятся из эксплуатации | — | PostgreSQL legacy | Strangler Fig: выключается после переноса последнего функционала |

### 3.3. Взаимодействие

| Откуда → куда | Способ | Почему |
|---|---|---|
| DSP → Edge RTB Gateway → Bidding | HTTPS/OpenRTB 2.6 (JSON, опционально Protobuf) → HTTP/2 | Стандарт отрасли; внутри — keep-alive и мультиплексирование |
| Bidding → User Profile | gRPC, тайм-аут 8 мс, fallback «без сегментов» | Нужен ответ в рамках запроса; бинарный протокол, низкий overhead |
| Bidding → Budget & Pacing | gRPC, асинхронно в фоне (продление lease), не на пути запроса | Глобальная координация бюджета без влияния на latency |
| Campaign → Bidding | Kafka `campaign.changes` (compacted) + gRPC-стрим снапшота при старте | Изменения доходят за секунды; старт инстанса без нагрузки на БД |
| Bidding, Event Collector → Kafka | Async, at-least-once, idempotent producer | Развязка hot path и обработки событий |
| Kafka → Statistics, Finance, Budget, Profile, Analytics | Consumer groups | Каждый потребитель читает поток независимо |
| Dashboard → API Gateway → BFF → сервисы | REST/JSON (внешне), gRPC (внутри) | Удобство фронтенда + эффективность внутри |
| Finance ↔ Payment Gateway | HTTPS REST + webhooks, идемпотентные ключи | Внешний контракт шлюза |

Детальная схема и обоснование протоколов — в [Task2/interaction.md](../Task2/interaction.md).

### 3.5. Мультирегиональное развёртывание

- **Два региона**, DSP маршрутизируются на ближайший через GeoDNS/Anycast.
- **RTB-контур (Edge Gateway, Bidding, Profile, Budget, Event Collector, Redis, Kafka)** — active-active: каждый регион самостоятельно обслуживает запросы. Бюджеты делятся между регионами квотами (lease), поэтому межрегиональная синхронизация не нужна на пути запроса.
- **Campaign и Finance** — primary в регионе A, асинхронная реплика в регионе B (Campaign) и синхронная реплика в соседней зоне + асинхронная в регионе B (Finance). Изменения кампаний реплицируются в регион B через Kafka MirrorMaker 2.
- **События** реплицируются в центральный регион (MirrorMaker 2) для финансов и аналитики.
- Подробнее: [Task3/failover.md](../Task3/failover.md).

### 3.6. Как целевая архитектура закрывает цели

| Цель | Решение |
|---|---|
| 50 000 RPS | Stateless Bidding (~2 500–3 000 RPS на под) × ~30 подов на два региона с запасом 50%; Kafka и ClickHouse шардированы |
| P95 ≤ 80 мс | Нет реляционной БД на hot path, данные в памяти и Redis, жёсткий тайм-аут-бюджет, no-bid вместо опоздания |
| SLA 99.9% | Нет SPOF, active-active RTB в двух регионах, автоматический failover БД, canary-релизы |
| Мультиплатформенность | Partner Config Service + адаптеры протоколов в Edge Gateway/Bidding; новый партнёр — конфигурацией |
| Event-driven | Kafka как шина фактов: аукционы, показы, клики, изменения кампаний, финансовые события |
| Горизонтальное масштабирование | Kubernetes HPA, шардирование Redis/ClickHouse/Kafka по ключам |
