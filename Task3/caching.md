# Стратегия кеширования

Диаграммы: [diagrams/caching-flow.puml](diagrams/caching-flow.puml), [diagrams/data-architecture.puml](diagrams/data-architecture.puml)

## 1. Уровни кеша

| Уровень | Где | Что | Задержка доступа |
|---|---|---|---|
| **L1 — in-process** | память пода Bidding Service | снапшот кампаний и креативов, индексы таргетинга, шаблоны `adm`, кеш eCPM | наносекунды–микросекунды |
| **L2 — Redis Cluster (hot path)** | отдельный кластер в каждом регионе, в той же AZ-группе, что и Bidding | бюджеты/lease, флаги пауз, сегменты, frequency caps, дедупликация событий | 0,3–1 мс |
| **L2 — Redis (management)** | отдельный небольшой кластер | кеш BFF кабинета, реалтайм-счётчики статистики, результаты отчётов | 1–2 мс |
| **CDN** | edge-узлы провайдера | креативы (изображения, видео, JS) | десятки мс у пользователя |

**Почему два Redis-кластера.** Кабинет и отчёты не должны вытеснять из памяти и нагружать CPU кластера, от которого зависит аукцион (bulkhead). Разные политики: в hot path-кластере `maxmemory-policy noeviction` для бюджетов, в management — `allkeys-lfu`.

**Размещение Redis.** В Kubernetes-кластере каждого региона (оператор, например, Redis Operator) или managed Redis в том же регионе; узлы распределены по 3 AZ, клиенты Bidding используют cluster-aware клиент с локальным чтением реплики только для некритичных ключей. Сетевой путь Bidding → Redis — в пределах одного региона (< 1 мс).

## 2. Что кешируем: TTL и инвалидация

| Данные | Уровень | Ключ | TTL | Инвалидация / обновление | Паттерн |
|---|---|---|---|---|---|
| **Кампании, таргетинг, ставки** | L1 Bidding | снапшот в памяти | без TTL; полная ресинхронизация каждые 10 мин (защита от пропущенных событий) | **событийная**: `campaign.changes` (compacted) → применение к копии и атомарная замена | read-through из Kafka (refresh-ahead) |
| **Флаг паузы/стопа кампании** | L2 hot | `paused:{campaign_id}` | 24 ч | записывается Campaign Service синхронно при паузе, удаляется при запуске | write-through, «быстрый канал» на случай лага CDC |
| **Креативы и шаблоны `adm`** | L1 Bidding + CDN | `creative_id:version` | L1 — до события изменения; CDN — 1 год (URL версионирован, immutable) | новая версия креатива = новый URL; старый не инвалидируется, просто перестаёт использоваться | cache-aside, versioned keys |
| **Бюджеты: расход за сутки** | L2 hot | `budget:{campaign_id}` | до конца суток + 1 ч | это **не кеш, а источник истины** Budget Store (AOF); изменяется атомарно Lua-скриптом | — |
| **Lease бюджета** | L1 (локальный счётчик) + L2 | `lease:{campaign_id}:{pod}` | 60 с | истекает автоматически, неизрасходованный остаток возвращается | lease |
| **Лимит дневного бюджета, ставки** | L1 (в снапшоте) | — | вместе со снапшотом | `campaign.changes` | событийная |
| **Баланс рекламодателя (флаг «нет средств»)** | L2 hot | `funds:{advertiser_id}` | 5 мин | событие `BalanceChanged` / `BalanceExhausted` → обновление; TTL — страховка | event-driven + TTL |
| **Сегменты пользователя** | L2 hot | `seg:{user_id}` | 30 дней (продлевается при обновлении) | перезаписывается Profile Service по событиям | write-behind из событий |
| **Frequency caps** | L2 hot | `fcap:{user_id}` (HASH) | равен периоду ограничения (обычно 24 ч) | `HINCRBY` по событию показа | — |
| **Кеш eCPM / pCTR** | L1 Bidding | `(campaign, placement_bucket)` | 30 с | истечение | refresh-ahead |
| **Метки уже записанных событий** | L2 hot | `dedup:{auction_id}:{type}` | 24 ч | ставится **только после** подтверждения записи в Kafka (`acks=all`); потеря метки безопасна — дубли отбрасываются потребителями по `event_id` | write-after-commit |
| **Конфигурация партнёров** | Envoy (в памяти) | — | — | push через xDS | — |
| **Список кампаний рекламодателя (кабинет)** | L2 mgmt | `bff:campaigns:{advertiser_id}` | 60 с | удаление ключа при записи через BFF + событие `campaign.changes` | cache-aside |
| **Реалтайм-статистика «сегодня»** | L2 mgmt | `rt:{campaign_id}:{date}` (HASH: imps, clicks, spend) | 48 ч | инкременты из Statistics consumer | write-through |
| **Результаты отчётов** | L2 mgmt | `report:{hash(query, params)}` | 5 мин (за сегодня), 24 ч (закрытые периоды) | истечение; закрытые периоды неизменны | cache-aside |
| **Баланс для отображения в кабинете** | — | — | **не кешируется** | читается из Finance (реплика), т.к. пользователь ожидает точность после пополнения | — |

### Почему так

- **Ставки и кампании** меняются редко относительно частоты чтения (≈ миллионы чтений на одно изменение) → кешируем полностью в L1 и инвалидируем событиями, а не TTL: TTL дал бы либо устаревшие данные, либо лишнюю нагрузку.
- **Бюджеты** — быстро меняющиеся данные, кеширование их «как есть» привело бы к перерасходу. Поэтому используется не кеш, а **lease**: инстанс получает право потратить ограниченную сумму и расходует её локально.
- **Пауза кампании** — самое чувствительное изменение (рекламодатель ждёт мгновенной остановки), поэтому дублируется через Redis-флаг, проверяемый на каждом запросе (≈ 0,3 мс, pipelining с запросом сегментов).

## 3. Защита от проблем кеширования

| Проблема | Решение |
|---|---|
| **Cache stampede** (одновременный промах по популярному ключу) | single-flight (одна загрузка на ключ в инстансе), блокировка `SET NX lock:{key}` с коротким TTL в management-кеше, stale-while-revalidate |
| **Одновременное истечение TTL** | jitter ±10% к TTL |
| **Пропуск события инвалидации** | версия снапшота = offset Kafka; периодическая полная ресинхронизация; сравнение контрольной суммы снапшота с Campaign Service раз в 10 мин |
| **Несогласованность после записи (read-your-writes в кабинете)** | после записи BFF удаляет ключ и возвращает данные из ответа Campaign Service, а не из кеша |
| **Отказ Redis** | circuit breaker → fallback (см. [Task2/reliability.md](../Task2/reliability.md)); L1 снапшот кампаний не зависит от Redis |
| **Hot keys** (популярная кампания) | данные кампаний в L1, а не в Redis; в Redis на горячих ключах — локальный микрокеш на 100 мс для флагов |

## 4. Прогрев кеша (cache warming)

| Сценарий | Как прогреваем |
|---|---|
| **Старт нового пода Bidding** | 1) загрузка снапшота: gRPC-стрим `StreamSnapshot` из Campaign Service (или из S3, если Campaign недоступен — снапшот сохраняется каждые 5 мин); 2) догон `campaign.changes` с offset снапшота; 3) открытие пулов соединений к Redis и Kafka; 4) прогон синтетических запросов для JIT/кешей CPU; 5) только после этого `readyz = true`. Дополнительно Envoy `slow_start_config` (окно 30 с) плавно наращивает трафик на новый под |
| **Деплой (canary)** | старые поды продолжают обслуживать трафик, пока новые не прошли readiness; `maxUnavailable = 0` |
| **Автоскейлинг при росте трафика** | HPA с упреждением (масштабирование по RPS, а не только CPU) + scheduled scaling перед известными пиками (вечерние часы); минимальный резерв подов — 30% |
| **Перезапуск/failover Redis (hot path)** | реплика с теми же данными становится master; при полной потере — восстановление из RDB/AOF; **бюджеты** пересчитываются из суммы `budget.spend` / агрегатов ClickHouse за сутки (job `budget-rebuild`, ≤ 2 мин), до завершения — lease выдаются консервативно (50% обычного размера) |
| **Сегменты пользователей после потери Redis** | восстановление из бэкапа RDB; отсутствующие профили заполняются по мере поступления событий (торговля без сегментов — штатный fallback) |
| **Кеш кабинета (management)** | не прогревается целенаправленно (cache-aside); после деплоя — job прогрева для топ-100 рекламодателей по активности |
| **Новый регион** | Bidding прогревается из снапшота регионального Campaign-реплики; Redis профилей заполняется через репликацию событий (MirrorMaker) за 24 ч до переключения трафика |

## 5. Метрики кеша

- `cache_hit_ratio{cache,key_type}` — цель: > 99% для L1 кампаний, > 95% для сегментов.
- `snapshot_lag_seconds` — отставание L1 от `campaign.changes`, алерт > 30 с.
- `redis_latency_p99`, `redis_memory_used_ratio` (алерт > 70%), `evicted_keys` (в hot path-кластере должно быть 0).
- `budget_overspend_ratio` — фактический перерасход относительно лимита, алерт > 1%.
