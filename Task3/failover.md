# Отказоустойчивость данных: RPO/RTO, резервное копирование, 12-factor

Диаграмма: [diagrams/multi-region-failover.puml](diagrams/multi-region-failover.puml)

## 1. Целевая доступность

SLA 99.9% через год = не более **43,8 мин** недоступности в месяц. Поэтому:
- отказ узла/пода/AZ не должен приводить к простою (автоматический failover за секунды);
- отказ региона — переключение RTB-трафика за минуты;
- ручные операции восстановления допустимы только для некритичных к SLA контуров (аналитика).

| **Budget Store (Redis)** | критичный | **≤ 1 с** (AOF `everysec`, реплика) | **≤ 30 с** (failover реплики), ≤ 5 мин (rebuild из событий) | Redis Cluster с репликами; потеря ≤ 1 с расхода компенсируется lease и пересчётом из `budget.spend`/ClickHouse |
| **User Profile Store** | важный (не блокирует аукцион) | ≤ 1 ч | ≤ 15 мин | реплики, RDB раз в час; аукцион работает без сегментов |

| **Finance Service + DB** | критичный (деньги) | **0**, в том числе при потере всего региона | **≤ 1 мин** (отказ узла/AZ), **≤ 15 мин** (отказ региона) | кворумная синхронная репликация `ANY 2 (fin_a2, fin_b1, fin_b2)` — каждая подтверждённая транзакция есть на диске минимум одной реплики в регионе B; Patroni quorum mode, DCS на 3 площадках, проверка перед открытием записи (см. раздел 4) |

| **Kafka (кластер целиком)** | критичный | 0 внутри региона; ≤ 1 мин между регионами (MirrorMaker 2) | ≤ 15 мин | RF = 3, MirrorMaker 2, архив в S3 |

## 3. Стратегия резервного копирования

| Хранилище | Инструмент | Расписание | Хранение | Куда | Проверка |
|---|---|---|---|---|---|
| **Finance DB** | pgBackRest | полный — еженедельно, дифференциальный — ежедневно, **WAL — непрерывно** | PITR 35 дней; месячные полные — 5 лет (финансовая отчётность) | S3 в другом регионе, Object Lock (WORM), шифрование | ежемесячное восстановление на стенд + сверка балансов |
| **Campaign DB** | pgBackRest | полный — еженедельно, инкрементальный — ежедневно, WAL — непрерывно | PITR 14 дней, еженедельные — 3 месяца | S3, другой регион | ежемесячное восстановление |
| **Монолит (переходный период)** | pgBackRest | то же, что Campaign | PITR 14 дней | S3 | **первая задача недели 1**: сейчас RPO определяется последним бэкапом |
| **ClickHouse** | clickhouse-backup | ежедневно (инкрементально по партициям) | 30 дней | S3 | ежеквартально; плюс возможность replay из Kafka/S3-архива |
| **Redis (Budget)** | RDB каждые 15 мин + AOF `everysec` | — | 48 ч | S3 | rebuild-процедура проверяется в chaos-тестах |
| **Redis (Profile)** | RDB ежечасно | — | 7 дней | S3 | — |
| **Kafka** | не бэкапится как БД: RF = 3 + MirrorMaker 2 + S3 Sink (архив событий) | непрерывно | 1 год (сырые), 5 лет (финансовые) | S3 | выборочный replay из архива ежеквартально |
| **Снапшот кампаний Bidding** | сохраняется Bidding | каждые 5 мин | 24 ч | S3 | используется при каждом холодном старте |
| **Конфигурация** (Kubernetes, Envoy, Partner Config) | GitOps | при каждом изменении | бессрочно | Git | — |
| **Секреты** | Vault (снапшоты Raft) | ежедневно | 30 дней | S3, шифрование | — |

Правила:
- **Правило 3-2-1**: 3 копии, 2 типа носителей (реплики + объектное хранилище), 1 копия в другом регионе.
- **Бэкап без проверки восстановления не считается бэкапом**: ежемесячные учения по восстановлению с замером фактического RTO.
- Бэкапы шифруются (KMS), доступ на удаление — только у отдельной роли, для Finance — Object Lock.

## 4. Finance: RPO = 0 при потере региона

### 4.1. Проблема прежней схемы

Ранее синхронными были только реплики в соседних AZ того же региона, а реплика в регионе B — асинхронной. Если регион A теряется целиком после подтверждения проводки, но до её доставки в регион B, то после переключения проводка исчезает из леджера, а баланс рекламодателя становится неверным. Значит, RPO = 0 при потере региона такая схема не обеспечивала.

### 4.2. Топология: кворумная синхронная репликация с обязательным участием региона B

| Узел | Регион / AZ | Роль |
|---|---|---|
| `fin_a1` | A / AZ-a | primary |
| `fin_a2` | A / AZ-b | синхронный кандидат кворума (быстрый локальный failover) |
| `fin_b1` | B / AZ-a | синхронный кандидат кворума |
| `fin_b2` | B / AZ-b | синхронный кандидат кворума |
| `fin_a3` | A / AZ-c | асинхронная реплика для отчётов и сверок (вне кворума) |

```ini
# postgresql.conf (управляется Patroni)
synchronous_commit        = on        # подтверждение после записи WAL на диск реплик кворума
synchronous_standby_names = 'ANY 2 (fin_a2, fin_b1, fin_b2)'
```

```yaml
# patroni.yml
synchronous_mode: quorum        # Patroni >= 4.0: кворумный режим, учёт LSN всех кандидатов
synchronous_mode_strict: true   # нет кворума → запись блокируется, а не продолжается без реплик
```

**Почему это гарантирует RPO = 0 при потере региона.** В кворуме три кандидата, и только один из них (`fin_a2`) находится в регионе A. Транзакция считается подтверждённой, когда её WAL записан на диск двух кандидатов, а значит **минимум одного узла в регионе B**. Клиент (Finance Service, а через него Kafka-offset и ответ кабинету) получает подтверждение только после `COMMIT`, то есть каждая операция, которую система считает выполненной, уже лежит на диске в регионе B.

**Цена решения:**

| Аспект | Влияние | Почему приемлемо |
|---|---|---|
| Задержка `COMMIT` | + RTT между регионами (10–30 мс в пределах континента) | Finance не на hot path; проводки идут батчами (~100 транзакций/с), PostgreSQL группирует коммиты (group commit) |
| Доступность записи | при недоступности обоих узлов региона B (авария B или разрыв связи) запись в Finance блокируется (strict mode) | списания приходят из Kafka (`billing.batches`, retention 14 дней) и просто копятся в lag; пополнения получают статус «в обработке». Аукцион не затронут: бюджеты работают на lease. Временный перевод в режим «только локальный кворум» — только решением дежурного с записью окна RPO > 0 в журнал инцидентов |

### 4.3. Восстановление: процедура до возобновления записи

1. **Изоляция старого primary (fencing).** DCS Patroni (etcd) развёрнут на трёх площадках: регион A, регион B и узел-свидетель в регионе C. После потери региона A кворум etcd сохраняется (B + C). Старый primary, если он жив, но изолирован, теряет лидерский ключ и через TTL (30 с) сам переходит в read-only. Это исключает «раздвоение» леджера.
2. **Выбор нового primary.** В quorum mode Patroni разрешает промоут, только если видит не менее `N − k + 1 = 3 − 2 + 1 = 2` кандидатов кворума. В регионе B это `fin_b1` и `fin_b2`, промоутится узел с наибольшим LSN. Так как каждая подтверждённая транзакция есть хотя бы на одном из них, после промоута леджер содержит **все** подтверждённые проводки. Второй узел догоняет новый primary и становится его синхронной репликой.
3. **Автоматическая проверка перед открытием записи** (job `finance-failover-verify`, ≤ 5 мин):
   - LSN нового primary ≥ максимального flush LSN, о котором сообщали участники кворума (из DCS/мониторинга);
   - двойная запись сходится: для каждой `tx_id` за последние 24 ч сумма проводок равна 0;
   - проекция `account_balances` совпадает с суммой проводок леджера по счетам, изменённым за последний час;
   - строки `outbox`, не опубликованные до аварии, на месте: Debezium в регионе B стартует с нового primary и публикует их (потребители идемпотентны, повтор безопасен).
4. **Возобновление записи.** Finance Service в регионе B масштабируется с 1 до рабочего числа подов, дежурный подтверждает переключение (одна кнопка в runbook, всё остальное автоматизировано). RTO ≤ 15 мин.
5. **Продолжение обработки входящих событий без потерь и дублей.** Finance сохраняет offset обработанных сообщений Kafka в таблице `consumer_offsets` **в той же транзакции**, что и проводку. Эти offset реплицируются вместе с леджером, и потребитель в регионе B продолжает с них (через трансляцию offset MirrorMaker 2). Повторно прочитанные события отбрасываются по `processed_events`.

### 4.4. Что не считается потерей подтверждённых операций

- **События, ещё не дошедшие до Finance** (например, `billing.batches` в Kafka региона A, не успевшие отреплицироваться MirrorMaker 2, лаг ≤ 1 мин), не были проведены и не подтверждены. Они дочитываются из Kafka региона A после его восстановления (данные на дисках брокеров), а при безвозвратной потере восстанавливаются сверкой с billing-отчётами DSP. Дублей не будет благодаря детерминированному `event_id`.
- **Пополнения в статусе «в обработке»** сверяются с платёжным шлюзом по idempotency key; шлюз также повторяет webhook.

### 4.5. Проверка

- Ежеквартальные учения: отключение региона A на стенде под нагрузкой проводок, затем сверка «подтверждённые операции до аварии = операции в леджере после промоута».
- Алерты: число синхронных кандидатов в кворуме < 3 (warning), < 2 (critical: запись заблокирована), задержка `COMMIT` P99 > 100 мс.

## 5. Сценарии отказов

| Сценарий | Автоматическая реакция | Влияние |
|---|---|---|
| Падение пода Bidding | Envoy outlier detection + Kubernetes перезапуск | нет |
| Отказ AZ | поды и брокеры в двух других AZ; Patroni переключает primary на синхронную реплику | кратковременный рост latency, без простоя |
| Отказ primary PostgreSQL (Campaign/Finance) | Patroni failover ≤ 30 с; для Finance — на кандидата кворума с наибольшим LSN | запись в кабинете/финансах недоступна ≤ 1 мин; аукцион не затронут |
| Отказ Redis master | Redis Cluster failover ≤ 15 с | аукцион на fallback (без сегментов, на lease) |
| Отказ Kafka-брокера | лидерство партиций переходит к репликам | нет |
| Недоступность Kafka целиком | Bidding — буфер логов аукционов (не оплачиваемые данные); Collector — 503 на win/bill (DSP повторит), клики — в надёжный локальный журнал | задержка статистики; аукцион работает; оплачиваемые события не теряются |
| Отказ ClickHouse-шарда | чтение с реплики; при потере обеих — восстановление из бэкапа + replay | задержка отчётов |
| Отказ региона | GeoDNS убирает регион (≤ 30 с), весь RTB-трафик уходит во второй регион, где **постоянно** развёрнута мощность на 50 000 RPS + 20% (27 подов Bidding, см. [Task1/TO-BE.md, 3.5](../Task1/TO-BE.md#35-мультирегиональное-развёртывание)) | ≤ 5 мин деградации RTB; Finance — промоут в регионе B без потери подтверждённых проводок (раздел 4), ≤ 15 мин; Campaign — промоут асинхронной реплики, ≤ 30 мин |
| Логическая ошибка (удаление данных, неверная миграция) | PITR на момент до ошибки в отдельный кластер, точечное восстановление | зависит от данных |

## 6. Соответствие принципам 12-factor

| # | Принцип | Как выполняется |
|---|---|---|
| I | **Codebase** — одна кодовая база, много развёртываний | у каждого сервиса свой репозиторий (или каталог в монорепо) и один артефакт для dev/stage/prod |
| II | **Dependencies** — явное объявление | Go modules, Conan/vcpkg (C++), Poetry (Python), npm lockfile; всё упаковано в Docker-образ |
| III | **Config** — конфигурация в окружении | переменные окружения и ConfigMap; секреты — Vault (через CSI/инжектор), не в коде и не в образе; квоты партнёров — Partner Config (xDS) |
| IV | **Backing services** — внешние ресурсы как подключаемые | PostgreSQL, Redis, Kafka, ClickHouse, S3 задаются URL/DSN из конфигурации; переключение на реплику/другой регион без пересборки |
| V | **Build, release, run** — строгое разделение | CI собирает неизменяемый образ (тег = git SHA) → release = образ + конфигурация (Helm values, Argo CD) → run в Kubernetes; откат = предыдущий release |
| VI | **Processes** — stateless-процессы | Bidding, Gateway, Collector, BFF не хранят состояние между запросами; снапшот кампаний — производный кеш, восстанавливается из Campaign/Kafka; бюджеты и профили — в Redis |
| VII | **Port binding** | каждый сервис сам слушает порт (HTTP/2, gRPC), без внешнего веб-сервера |
| VIII | **Concurrency** — масштабирование процессами | горизонтальное масштабирование подами (HPA, KEDA по lag); разные типы процессов (web, consumer, job) — разные Deployment |
| IX | **Disposability** — быстрый старт и корректное завершение | старт Bidding ≤ 30 с (снапшот из стрима/S3), `preStop` + graceful shutdown: снятие с балансировки, доработка запросов, flush Kafka-продюсера, коммит offset |
| X | **Dev/prod parity** | одинаковые образы и версии backing services (Docker Compose/Testcontainers локально, staging = уменьшенная копия prod); нагрузочный стенд воспроизводит пик |
| XI | **Logs** — поток событий | логи в stdout в JSON с `trace_id`, сбор Fluent Bit → Loki; сервисы не управляют файлами логов |
| XII | **Admin processes** | миграции схем (Flyway/Liquibase/golang-migrate), rebuild бюджетов, переотправка DLQ — как одноразовые Kubernetes Job из того же образа и релиза |

**Отклонения и компромиссы:**
- Bidding держит в памяти крупный снапшот — это не нарушает фактор VI, так как это кеш, но увеличивает время старта (IX). Компенсация — снапшот в S3 и стрим из Campaign, прогрев до readiness.
- Redis и Kafka в hot path — backing services (IV), но с жёсткими требованиями к latency; поэтому они размещаются в том же регионе и подключаются через cluster-aware клиентов с тайм-аутами и circuit breaker.
