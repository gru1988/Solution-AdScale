# Стратегия данных: Database per Service

Диаграмма: [diagrams/data-architecture.puml](diagrams/data-architecture.puml)

## 1. Принципы

1. **Каждый сервис — единственный владелец своих данных.** Другие сервисы получают их через API (gRPC) или события (Kafka), но не читают чужие таблицы.
2. **Хранилище подбирается под профиль нагрузки**, а не «одна СУБД на всё»: OLTP, KV с микросекундным доступом, OLAP и поток событий — разные задачи.
3. **Согласованность между сервисами — eventual** через события (Transactional Outbox + CDC). Строгая согласованность — только внутри сервиса (финансы).
4. **Минимум разных технологий**: PostgreSQL, Redis, ClickHouse, Kafka, S3 покрывают все сценарии; команда без SRE не должна поддерживать «зоопарк».

## 2. Выбор хранилища для каждого сервиса

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| **Сервис ставок (Bidding)** | **In-memory снапшот в процессе (L1) + Redis Cluster (KV)**; собственной персистентной БД нет | Hot path ≤ 80 мс: любые сетевые обращения к реляционной БД недопустимы. Данные кампаний читаются из памяти (микросекунды), бюджетные lease, frequency caps и сегменты — из Redis (≈ 0,5–1 мс). Сервис stateless: всё, что ему нужно, восстанавливается из Campaign Service/Kafka и Budget Store. Результаты аукционов не хранит, а публикует в Kafka |
| **Сервис кампаний (Campaign)** | **PostgreSQL** (реляционная, ACID) + Patroni HA | Сложная связанная модель (рекламодатель → кампании → группы → креативы → таргетинг → расписания), транзакционные изменения, ограничения целостности, умеренный объём (единицы ГБ) и низкий RPS записи (изменения из кабинета). JSONB для гибких правил таргетинга. Для публикации изменений — таблица `outbox` + Debezium |
| **Сервис статистики (Statistics)** | **Kafka (вход) + ClickHouse (колоночная OLAP-СУБД) + Redis (реалтайм-счётчики)** | Write-heavy поток (десятки тысяч событий/с), append-only, данные не обновляются. ClickHouse принимает миллионы строк/с батчами, сжимает в 10–20 раз, агрегирует через `AggregatingMergeTree`/материализованные представления. Redis — счётчики «за сегодня» для кабинета с задержкой в секунды |
| **Сервис аналитики (Analytics)** | **ClickHouse (выделенные реплики для чтения)** — тот же кластер данных событий, отдельные реплики/кластер для тяжёлых запросов; витрины кампаний — через словари ClickHouse из Campaign | Тяжёлые агрегаты и произвольные срезы по миллиардам строк — задача колоночной СУБД; запросы к PostgreSQL (как сейчас) блокируют OLTP. Аналитика только читает: собственная запись не нужна, кроме сохранённых отчётов (небольшая схема в PostgreSQL BFF/Analytics или в ClickHouse) |
| **Сервис финансов (Finance)** | **PostgreSQL** (выделенный кластер, синхронная репликация) | Деньги требуют ACID, сериализуемых проводок, уникальных ограничений для идемпотентности, аудита и PITR. Двойная запись (double-entry) естественно ложится на реляционную модель. Объём (агрегированные проводки) — десятки ГБ в год, укладывается в один primary с партиционированием по месяцам |

### Дополнительные сервисы целевой архитектуры

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| Budget & Pacing | **Redis Cluster** (источник истины для расхода за текущие сутки, AOF) + периодические снапшоты в PostgreSQL Finance/Campaign | Атомарные инкременты и Lua-скрипты на сотнях тысяч операций/с; ежесуточное закрытие дня фиксируется в Finance; при потере Redis расход восстанавливается из ClickHouse |
| User Profile | **Redis Cluster** на старте → **Aerospike** при росте > 100 ГБ | KV-доступ по `user_id` за ≤ 1 мс, TTL на записи; Aerospike — гибрид RAM-индекс + SSD-данные, дешевле Redis на больших объёмах |
| Event Collector | нет (Kafka) + Redis для дедупликации | Stateless-приёмник |
| Creative Delivery | **S3** + CDN; метаданные — в Campaign DB | Бинарные файлы, раздача через CDN |
| Partner Config | **PostgreSQL** (отдельная схема в кластере Campaign) | Малый объём, редкие изменения, транзакционность |
| Advertiser BFF | нет (только кеш Redis) | Агрегирует данные других сервисов |

## 3. Владение данными (кто — источник истины)

| Сущность | Владелец | Потребители | Канал |
|---|---|---|---|
| Кампании, креативы, таргетинг, ставки | Campaign | Bidding, Analytics, BFF, Finance (справочно) | `campaign.changes` (Kafka, compacted), gRPC |
| Партнёры (DSP/SSP) | Partner Config | Edge Gateway, Bidding, Analytics | xDS, `partner.changes` |
| Результаты аукционов | Bidding (продюсер) | Statistics, Analytics | `auction.results` |
| Показы, клики, win/billing | Event Collector (продюсер) | Statistics, Budget, Profile, Finance | `ad.impressions`, `ad.clicks` |
| Расход за текущие сутки, lease | Budget & Pacing | Bidding, BFF | gRPC, `budget.spend` |
| Проводки, балансы, счета | Finance | BFF, Budget (лимиты), Analytics | gRPC, `finance.charges` |
| Профили пользователей | User Profile | Bidding | gRPC |
| Агрегированная статистика | Statistics | Analytics, BFF, Finance (`billing.batches`) | ClickHouse, Kafka |

## 4. Согласованность между сервисами

| Сценарий | Паттерн |
|---|---|
| Изменение кампании → аукцион | Transactional Outbox + Debezium → `campaign.changes`; задержка 1–3 с |
| Показы → списания | Statistics агрегирует → `billing.batches` → Finance (идемпотентный Inbox) |
| Пополнение баланса → разблокировка кампаний | **Saga (хореография)**: `PaymentReceived` (Payment Adapter) → Finance проводит → `BalanceChanged` → Budget пересчитывает лимиты → Campaign снимает статус `OUT_OF_FUNDS`. Компенсация: `PaymentReversed` → сторно в Finance → `BalanceChanged` |
| Исчерпание баланса | Finance публикует `BalanceExhausted` → Budget обнуляет lease → кампании выбывают из аукциона за ≤ 60 с |

## 5. Миграция с общей PostgreSQL

1. **Разметка схемы монолита по владельцам** (таблицы кампаний, финансов, статистики, аналитики) и запрет межмодульных JOIN в коде (модульный монолит).
2. **Статистика**: новые события пишутся только в Kafka → ClickHouse; исторические данные выгружаются из PostgreSQL в ClickHouse один раз; таблицы событий в PostgreSQL удаляются → основная разгрузка БД.
3. **Аналитика**: сначала на read replica PostgreSQL, затем на ClickHouse.
4. **Campaign**: схема переносится в отдельный кластер (логическая репликация PostgreSQL → новый кластер, переключение записи с коротким окном read-only), монолит переводится на gRPC API Campaign Service.
5. **Finance**: аналогично, с двойной записью и сверкой в течение одного расчётного периода перед переключением.
6. Общая БД монолита выключается после переноса последней схемы.
