# ADR-003. Выбор технологии для потоковой обработки событий

- **Статус:** Принято
- **Дата:** 2026-11-15
- **Связанные решения:** [ADR-001](ADR-001-evolution-strategy.md), [ADR-002](ADR-002-bidding-service-first.md), [Task3/event-streaming.md](../../Task3/event-streaming.md)

## Контекст

- Statistics Service пишет показы и клики напрямую в PostgreSQL без буферизации; при 15 000 RPS это порядка 10–20 тыс. INSERT/с, конкурирующих с транзакционными запросами и аукционом.
- Через 3 месяца поток вырастет на 20%, через год — примерно в 3,3 раза (50 000 RPS → десятки тысяч событий в секунду, ~50 МБ/с).
- Одни и те же события нужны нескольким потребителям: статистике, финансам (списания), pacing бюджета, профилям пользователей (frequency capping), аналитике, антифроду.
- Требования: не терять оплачиваемые события, возможность повторной обработки (replay), порядок событий в рамках кампании, мультирегиональная репликация, низкая стоимость, open-source.

## Рассмотренные варианты

| Критерий | **Apache Kafka** | RabbitMQ | Apache Pulsar | Redis Streams | Managed (Kinesis / Pub/Sub) |
|---|---|---|---|---|---|
| Пропускная способность (50+ МБ/с) | отлично | средне (при persistence) | отлично | ограничена памятью | хорошо, но квоты на шард |
| Хранение и replay | да, по retention, log compaction | нет (сообщение удаляется) | да, tiered storage | ограниченно | 1–7 дней |
| Независимые потребители одного потока | consumer groups | нужны отдельные очереди на потребителя | subscriptions | consumer groups | да |
| Порядок по ключу | в партиции | ограниченно | в партиции | в стриме | в шарде |
| Экосистема (CDC, коннекторы, ClickHouse) | Debezium, Kafka Connect, ClickHouse Kafka Engine, Schema Registry | слабая | меньше | слабая | vendor lock-in |
| Мультирегион | MirrorMaker 2 | federation/shovel | geo-replication встроена | нет | ограничено облаком |
| Экспертиза на рынке / в команде | очень высокая | высокая | низкая | высокая | средняя |
| Операционная сложность | средняя (KRaft без ZooKeeper) | низкая | высокая (брокеры + BookKeeper) | низкая | минимальная |

## Решение

Используем **Apache Kafka (KRaft) + Schema Registry с форматом Avro**:

- Кластер: 3 брокера на старте (6 через год, на регион), `replication.factor=3`, `min.insync.replicas=2`.
- Продюсеры hot path: `acks=all`, `enable.idempotence=true`, батчинг (`linger.ms=5`, `compression.type=lz4`); публикация асинхронная, вне пути ответа DSP.
- Ключ партиционирования — `campaign_id` для событий, влияющих на бюджет и статистику (порядок и локальность агрегатов).
- Потребители — отдельные consumer groups: `statistics`, `finance-billing`, `budget-pacing`, `profile-updater`, `analytics-loader`, `bidding-snapshot`.
- Запись в ClickHouse — батчами (через Kafka Engine/consumer), запись в PostgreSQL финансов — агрегатами по минутам.
- Для промежуточного решения допускается managed Kafka, чтобы снизить нагрузку на команду без SRE.

## Последствия

**Положительные**
- Запись событий убирается из hot path и из PostgreSQL: нагрузка на БД по записи падает на порядки (батчи и агрегаты вместо отдельных INSERT).
- Один поток — много потребителей; новые потребители (антифрод, ML) подключаются без изменений продюсеров.
- Replay по retention: можно пересчитать статистику или восстановить ClickHouse после аварии.
- Kafka становится основой event-driven архитектуры и CDC (Debezium) для Strangler Fig.

**Отрицательные и риски**
- Семантика at-least-once → потребители обязаны быть идемпотентными (дедупликация по `event_id`, уникальные ключи в финансах).
- Операционная сложность (мониторинг лагов, ребалансировки, диски) → managed-сервис или выделенный владелец платформы, алерты на consumer lag.
- Eventual consistency статистики (секунды) → приемлемо по FR-10 (≤ 1 мин).
- Эволюция схем → Schema Registry с режимом совместимости `BACKWARD`.
