## 2. Стратегия по сервисам

| Сервис / хранилище | Репликация | Шардирование | Read replicas | CQRS |
|---|---|---|---|---|
| Bidding (in-memory) | не нужна: каждый под держит полную копию снапшота | нет (снапшот ~250 МБ помещается в память); через год — опционально по региону | — | является **read side** модели кампаний |
| Redis Cluster (бюджеты, профили, caps) | master–replica для каждого шарда, автоматический failover | **да**, hash slots; ключи с hash tag | реплики не используются для чтения бюджетов (нужна свежесть), для профилей — допустимо | — |
| Campaign DB (PostgreSQL) | **master–slave**: Patroni, 1 синхронная реплика (другая AZ) + 1 асинхронная (+ асинхронная в регионе B) | **нет**: объём единицы ГБ, запись редкая | **да**: стартовые снапшоты Bidding, отчёты кабинета | **да** |
| ClickHouse (Statistics/Analytics) | ReplicatedMergeTree, 2 реплики на шард (ClickHouse Keeper) | **да**, по `campaign_id` | **да**: отдельный набор реплик для Analytics | **да** (query side) |
| Finance DB (PostgreSQL) | **master–slave с кворумной синхронной репликацией** `ANY 2 (fin_a2, fin_b1, fin_b2)` — подтверждение обязательно включает реплику в регионе B (RPO = 0 и при потере региона) + асинхронная реплика для отчётов | **нет** в горизонте года; партиционирование леджера по месяцам. Подготовка к шардированию по `advertiser_id` (Citus) | **да**: отчёты и сверки | **да** (леджер → проекции балансов) |
| Kafka | RF = 3, `min.insync.replicas = 2` | партиции по `campaign_id` | — | шина между write и read side |

## 3. Репликация master–slave

### Где применяем

| Кластер | Топология | Режим | Зачем |
|---|---|---|---|
| **Finance** | primary (A, AZ-a) + кандидаты кворума: `fin_a2` (A, AZ-b), `fin_b1`, `fin_b2` (регион B) + async replica `fin_a3` (A, AZ-c, отчёты) | `synchronous_commit = on`, `synchronous_standby_names = 'ANY 2 (fin_a2, fin_b1, fin_b2)'`, Patroni `synchronous_mode: quorum`, `synchronous_mode_strict: true` | В кворуме только один узел региона A, поэтому любая подтверждённая проводка записана минимум на одной реплике региона B: RPO = 0 при отказе узла, AZ **и всего региона**. Отказ одного любого кандидата запись не блокирует. Цена — +RTT между регионами на `COMMIT` (Finance не на hot path). Подробно: [failover.md, раздел 4](failover.md#4-finance-rpo--0-при-потере-региона) |
| **Campaign** | primary + sync standby + async replica + async replica (регион B) | `synchronous_commit = on` для изменений, `remote_write` допустим | HA, разгрузка чтений (снапшоты, кабинет), DR |
| **Монолит (переходный период)** | primary + standby (HA) + read replica (аналитика) | async | Снять аналитику с primary уже в первый месяц |
| **Redis** | 1 replica на каждый master-шард, Redis Cluster failover | async | Быстрый failover (секунды); потеря последних мс записей компенсируется lease/сверкой |
| **ClickHouse** | 2 реплики на шард | асинхронная, через Keeper | Отказоустойчивость и масштабирование чтения |

Failover PostgreSQL — **Patroni** (etcd/Consul в Kubernetes) с автоматическим переключением ≤ 30 с; клиенты подключаются через **PgBouncer** + Service по роли (`primary`/`replica`). Защита от split-brain — fencing через DCS и `pg_rewind` старого primary.

## 4. Шардирование

| Данные | Ключ | Схема | Почему этот ключ |
|---|---|---|---|
| **События в ClickHouse** (`events_raw`, агрегаты) | `campaign_id` | `Distributed`-таблица, `sharding_key = cityHash64(campaign_id)`; внутри шарда `PARTITION BY toYYYYMMDD(ts)`, `ORDER BY (campaign_id, event_type, ts)` | Почти все запросы фильтруют по кампании/рекламодателю → запрос попадает на один шард; равномерность обеспечивается хешем. Через год — 6 шардов × 2 реплики |
| **Бюджеты в Redis** | `campaign_id` с hash tag: `budget:{cmp-1042}`, `lease:{cmp-1042}:pod-7` | Redis Cluster, 16 384 слота | Все ключи кампании — в одном слоте, Lua-скрипт lease атомарен на одном узле |
| **Профили / caps в Redis** | `user_id`: `seg:{u}`, `fcap:{u}` | Redis Cluster | Равномерное распределение по миллионам пользователей, все данные пользователя на одном узле |
| **Kafka-топики** | `campaign_id` (события, бюджеты, финансы), `request_id` (лог аукционов без победителя) | партиционирование по хешу ключа | Порядок событий кампании и локальность агрегатов у потребителя |
| **Finance (через 1–2 года при необходимости)** | `advertiser_id` | Citus (distributed tables) | Все проводки и балансы рекламодателя — на одном шарде, транзакции не распределённые |

Что **не** шардируем и почему:
- **Campaign DB** — небольшой объём и нагрузка; шардирование усложнит транзакции и отчёты без выгоды. Чтения масштабируются репликами и кешем.
- **Finance DB** в горизонте года — объём агрегированных проводок (~2–3 млн строк/сутки) обслуживается одним primary с партиционированием по месяцам; шардирование финансов — дорогое и рискованное изменение, откладываем до появления измеримой потребности.
- **Hot spots**: крупная кампания может создать перекос в ClickHouse и Kafka → для топ-кампаний в Kafka используется составной ключ `campaign_id + bucket(0..7)` в топике `auction.results`; ClickHouse переносит перекос лучше, т.к. агрегаты считаются по всем шардам параллельно.

## 5. Read replicas для сервиса аналитики

**Да, нужны — в два этапа.**

1. **Переходный период (недели 2–4)**: асинхронная streaming-реплика PostgreSQL монолита, Analytics-модуль переключается на неё.
   - `hot_standby_feedback = off`, `max_standby_streaming_delay = 5min` — тяжёлые запросы не влияют на primary (ценой возможной отмены очень долгих запросов на реплике);
   - отдельный пул PgBouncer, `statement_timeout = 5min`.
2. **Целевое состояние**: Analytics читает только ClickHouse. В каждом шарде выделяется реплика (или отдельный replica-set) для аналитических запросов: `load_balancing = in_order` с приоритетом аналитических реплик, `max_threads`/`max_memory_usage` и квоты через профили пользователей ClickHouse. Запись (Statistics) и реалтайм-чтения кабинета идут на другие реплики.

## 6. CQRS

| Домен | Command side (запись) | Query side (чтение) | Синхронизация | Зачем |
|---|---|---|---|---|
| **Кампании** | Campaign Service → PostgreSQL | снапшот в памяти Bidding; кеш BFF в Redis; словари в ClickHouse | Outbox → Kafka `campaign.changes` | Модель записи нормализована для целостности, модель чтения — инвертированные индексы для аукциона за микросекунды |
| **Статистика и аналитика** | Event Collector / Bidding → Kafka (append-only факты) | ClickHouse: сырые события + материализованные представления (минутные/часовые агрегаты); Redis-счётчики «сегодня» | Kafka consumers | Запись — поток фактов, чтение — агрегаты по произвольным срезам |
| **Финансы** | Finance → леджер (неизменяемые проводки) | проекция `account_balances`, витрины счетов на async-реплике и в ClickHouse | транзакционно (баланс) и через Outbox (витрины) | Леджер — аудит и неизменяемость; баланс и отчёты — быстрые чтения |

**Где CQRS не применяем:** Partner Config, User Profile, Budget — простые модели, где разделение не даёт выгоды.

## 7. Горизонтальное масштабирование вычислений

| Компонент | Механизм | Триггер |
|---|---|---|
| Bidding, Edge Gateway, Event Collector | Kubernetes HPA | CPU 60%, RPS на под, P95 latency |
| Kafka consumers | число подов ≤ числа партиций; KEDA по consumer lag | lag > 10 000 сообщений или > 30 с |
| ClickHouse | добавление шардов + ребалансировка новых партиций | диск > 70%, P95 запросов |
| Redis Cluster | добавление master-узлов + resharding слотов онлайн | память > 70%, ops/s |
