# Архитектурные драйверы

## 1. Бизнес-цели

| ID | Цель | Срок | Метрика успеха |
|---|---|---|---|
| BG-1 | Подключить новую DSP-площадку без нарушения её SLA | 3 месяца | P95 ≤ 80 мс на трафике DSP, 0 штрафов в первый месяц |
| BG-2 | Удержать текущих клиентов, не ухудшив их сервис | постоянно | P95 ≤ 100 мс для всех, жалобы в поддержку не растут |
| BG-3 | Выдержать рост трафика | 3 месяца / 1 год | 18 000 RPS (с запасом до 25 000) / 50 000 RPS |
| BG-4 | Подготовить платформу к мультиплатформенной интеграции (несколько DSP/SSP) | 1 год | новый партнёр подключается конфигурацией, без изменения кода ядра |
| BG-5 | Обеспечить непрерывность бизнеса во время миграции | постоянно | нет плановых простоев hot path |

## 2. Функциональные требования (после интеграции)

### RTB и показ рекламы

| ID | Требование |
|---|---|
| FR-1 | Принимать bid request от нескольких DSP по протоколу **OpenRTB 2.5/2.6** (JSON поверх HTTPS), с конфигурацией на уровне партнёра (эндпоинт, квоты, тайм-аут, формат) |
| FR-2 | Определять пользователя (cookie/device ID, сегменты) и подбирать кандидатов-кампаний по таргетингу: гео, устройство, ОС, площадка, сегменты, расписание, частотные ограничения (frequency capping) |
| FR-3 | Проводить аукцион: применять бизнес-правила, floor price, pacing бюджета, определять победителя и цену |
| FR-4 | Возвращать bid response (ставка, креатив/adm, nurl/burl) или no-bid (HTTP 204) в пределах тайм-аута партнёра |
| FR-5 | Обрабатывать win notice, billing notice, показы и клики; регистрировать каждое событие ровно один раз в учёте |
| FR-6 | Не допускать перерасхода бюджета кампании выше заданного порога (например, ≤ 1% дневного бюджета) |

### Управление и финансы

| ID | Требование |
|---|---|
| FR-7 | Рекламодатель создаёт и редактирует кампании, креативы, таргетинг, бюджеты и ставки через кабинет; изменения доходят до аукциона не позже чем за 30 с |
| FR-8 | Пополнение баланса через платёжный шлюз, списание за показы/клики, выставление счетов, сверка балансов |
| FR-9 | Финансовые операции идемпотентны: повторная доставка события или запроса не приводит к двойному списанию |

### Аналитика и отчётность

| ID | Требование |
|---|---|
| FR-10 | Почти реалтайм-статистика по кампаниям (показы, клики, CTR, расход) с задержкой ≤ 1 мин |
| FR-11 | Исторические отчёты и произвольные срезы без влияния на работу аукциона |
| FR-12 | Отчётность для DSP-партнёров: объём запросов, доля ответов, win rate, latency, ошибки |

## 3. Атрибуты качества (с приоритизацией)

Приоритет определён по методу utility tree: **(H, H)** — высокая важность для бизнеса и высокая сложность реализации.

| Приоритет | Атрибут | Сценарий / измеримое требование | (Важность, Сложность) |
|---|---|---|---|
| 1 | **Производительность (latency)** | При 18 000 RPS P95 обработки bid request ≤ 80 мс для нового DSP и ≤ 100 мс для остальных; P99 ≤ 120 мс; внутренний жёсткий тайм-аут 70 мс → no-bid | (H, H) |
| 2 | **Масштабируемость** | Рост трафика до 50 000 RPS обрабатывается добавлением инстансов hot path без изменения кода; автоскейлинг за ≤ 3 мин | (H, H) |
| 3 | **Доступность** | Промежуточно: 99.5% для RTB. Через год: SLA 99.9% (≤ 43,8 мин простоя в месяц); отказ одного инстанса не виден DSP | (H, H) |
| 4 | **Отказоустойчивость / изоляция** | Отказ аналитики, статистики, кабинета или финансов не влияет на аукцион; при отказе Redis аукцион продолжает работать на локальном кеше | (H, M) |
| 5 | **Целостность данных (финансы)** | Ни одно оплачиваемое событие не теряется и не учитывается дважды; RPO = 0 для финансов | (H, M) |
| 6 | **Наблюдаемость** | Для каждого запроса есть трейс; метрики P50/P95/P99 по каждому шагу и партнёру; алерт при нарушении SLO за ≤ 1 мин | (M, M) |
| 7 | **Модифицируемость / расширяемость** | Новый DSP подключается конфигурацией за ≤ 1 день; сервисы деплоятся независимо | (M, M) |
| 8 | **Развёртываемость** | Релиз hot path — canary с автоматическим откатом за ≤ 5 мин; без даунтайма | (M, M) |
| 9 | **Безопасность** | mTLS/ключи для DSP, OAuth2/JWT для кабинета, PCI-зона для платёжной интеграции, аудит финансовых операций | (M, L) |
| 10 | **Стоимость** | Рост инфраструктурных затрат не опережает рост трафика (стоимость 1 млн запросов не растёт) | (M, L) |

### Компромиссы между атрибутами

- **Latency ↔ консистентность.** В аукционе выбираем eventual consistency для кампаний и бюджетов (данные из кеша с задержкой ≤ 30 с), компенсируя риск перерасхода механизмом выделения бюджета порциями (budget leasing). В финансах — строгая консистентность.
- **Latency ↔ надёжность.** На hot path нет повторных попыток (не укладываемся в 80 мс): вместо retry — fallback и no-bid. Retry применяются только в асинхронных потоках.
- **Скорость миграции ↔ стоимость.** Не переписываем всё: выносим только то, что снимает главный риск, остальное остаётся в модульном монолите.

## 4. Ограничения

### Бизнес-ограничения

| ID | Ограничение | Влияние на архитектуру |
|---|---|---|
| BC-1 | Срок промежуточного решения — **3 месяца** | Только инкрементальные изменения с наибольшим эффектом; Strangler Fig |
| BC-2 | **Ограниченный бюджет** | Open-source (Kafka, Redis, ClickHouse, Envoy, Prometheus); облачные managed-сервисы — только где окупаются отсутствием SRE |
| BC-3 | **Непрерывность бизнеса** | Нет Big Bang-релиза; переключения через feature flags, shadow traffic, canary |
| BC-4 | Штрафы DSP за latency и downtime | Приоритет latency и доступности над функциональностью |
| BC-5 | Команда **35 человек**, нет SRE, техписателя и бизнес-аналитика | Простые и распространённые технологии; минимум собственной инфраструктуры; документация как часть работы (ADR, C4) |

### Технические ограничения

| ID | Ограничение | Влияние на архитектуру |
|---|---|---|
| TC-1 | Нельзя переписать систему полностью | Переиспользуем код Ad Server/Auction Engine (C++/Go) в новом сервисе |
| TC-2 | Гибридный стек C++ / Go / Python / Node.js | Сохраняем: C++/Go — hot path, Python — данные/аналитика, Node.js — UI/BFF. Межсервисный контракт — gRPC/Protobuf и Avro, независимый от языка |
| TC-3 | Одна PostgreSQL с общей схемой | Разделение данных поэтапно: сначала реплики и вынос потоков, затем Database per Service |
| TC-4 | Нет контейнеризации и CI/CD | Сначала контейнеризуется hot path, полный переход в Kubernetes — в течение года |
| TC-5 | Протокол DSP — OpenRTB | Внешний контракт фиксирован стандартом; внутренний — свободный выбор |
| TC-6 | Архитектура не задокументирована | Первая фаза включает реверс-инжиниринг зависимостей (трассировка, анализ схемы БД) |

## 5. Допущения

- Средний размер bid request — 1–2 КБ, события показа/клика — ~0,5 КБ в Avro.
- Win rate — 10–20%, CTR — около 1%; основной поток событий — лог аукционов и показы.
- Количество активных кампаний — десятки тысяч: полный снапшот для аукциона помещается в память инстанса (сотни МБ).
- Тайм-аут на стороне DSP — 100 мс, SLA ответа — 80 мс на нашей стороне.
