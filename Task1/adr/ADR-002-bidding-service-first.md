# ADR-002. Выделение сервиса ставок (Bidding Service) в качестве первого приоритета

- **Статус:** Принято
- **Дата:** 2026-11-15
- **Связанные решения:** [ADR-001](ADR-001-evolution-strategy.md), [ADR-003](ADR-003-event-streaming-technology.md)

## Контекст

- SLA нового DSP: P95 ≤ 80 мс; текущий P95 — 110–120 мс. Опоздавший ответ равен no-bid и потерянной выручке, а деградация штрафуется.
- По оценке бюджета времени (см. [AS-IS.md](../AS-IS.md), п. 2) 50–80 мс приходится на синхронные обращения Ad Server и Auction Engine к PostgreSQL. Бизнес-логика аукциона занимает единицы миллисекунд.
- Ad Server и Auction Engine нельзя масштабировать отдельно от монолита.
- Нужно выбрать, с какого компонента начать декомпозицию, чтобы за 3 месяца выполнить SLA.

## Рассмотренные варианты

| Вариант | Эффект на latency аукциона | Сложность за 3 мес. | Риск |
|---|---|---|---|
| A. Начать с Statistics (вынести запись событий) | Косвенный: снижает конкуренцию за БД, но чтения аукциона остаются синхронными | низкая | SLA 80 мс не гарантируется |
| B. Начать с Analytics (read replica / ClickHouse) | Косвенный, убирает пики | низкая | то же |
| C. Начать с Campaign Service | Почти нет: аукцион по-прежнему ходит за данными по сети | высокая (много связей с UI и финансами) | долгий срок |
| **D. Начать с Bidding Service** (Ad Server + Auction Engine), данные в памяти и Redis | **Прямой: убирает 40–60 мс** | средняя: код переиспользуется | средний, управляем через shadow/canary |

## Решение

1. **Первым выносится Bidding Service**, объединяющий логику Ad Server и Auction Engine в одном stateless-процессе (C++ ядро аукциона переиспользуется, обвязка — Go).
2. Объединение Ad Server и Auction Engine в один сервис осознанно: это один ограниченный контекст «принятие решения о ставке» с общим профилем нагрузки; разделение добавило бы сетевой переход (1–3 мс) и ещё одну точку отказа на hot path.
3. Сервис **не обращается к PostgreSQL на пути запроса**:
   - снапшот активных кампаний, креативов, таргетинга и ставок хранится в памяти процесса (индексы по гео, устройству, сегментам);
   - начальная загрузка — из read replica (позже — gRPC-стрим Campaign Service), обновления — из Kafka-топика `campaign.changes` (CDC);
   - бюджеты и pacing — через локальные порции бюджета (lease) и Redis, frequency caps и сегменты — Redis.
4. Все события (результат аукциона) публикуются в Kafka асинхронно.
5. Параллельно, силами другой части команды, выполняются **варианты A и B** (Kafka для статистики, read replica для аналитики): они дешёвые и снижают нагрузку на БД для остальных модулей.
6. Переключение: shadow traffic (сравнение решений старого и нового аукциона) → canary для текущих DSP → подключение нового DSP.

## Последствия

**Положительные**
- Прямое снижение P95 до ≈ 30–55 мс с учётом сети; независимое горизонтальное масштабирование аукциона.
- Изоляция отказов: проблемы монолита (UI, отчёты, финансы) не влияют на ставки.
- Новый сервис сразу строится с наблюдаемостью, тайм-аут-бюджетом и паттернами надёжности.

**Отрицательные и риски**
- Данные кампаний в аукционе отстают от источника на секунды (eventual consistency) → допустимо по FR-7 (≤ 30 с); паузы кампаний доходят через `campaign.changes` с приоритетом.
- Риск перерасхода бюджета при распределённом учёте → lease бюджета порциями, максимальный перерасход ограничен суммой невыбранных lease (≤ 1% дневного бюджета).
- Расхождение логики старого и нового аукциона → shadow-сравнение, допустимое расхождение решений < 0,1% до перехода на canary.
- Потребление памяти: снапшот на каждый инстанс (оценка — сотни МБ) → приемлемо; при росте — шардирование индекса по партнёрам/регионам.
