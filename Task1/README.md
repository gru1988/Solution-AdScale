## Главные выводы

1. **Корневая причина деградации** — общая PostgreSQL, в которой одновременно живут hot path аукциона (синхронное чтение), поток записи событий (≈ десятки тысяч INSERT/с без буферизации), финансовые транзакции и тяжёлая аналитика. Любой всплеск в одном потоке бьёт по P95 аукциона.
2. **Масштабировать монолит нечем**: нет кеша, нет очередей, нет контейнеризации, а Ad Server и Auction Engine нельзя масштабировать отдельно от остальных модулей.
3. **Стиль эволюции** — Strangler Fig с элементами модульного монолита: из монолита по одному выносятся критичные по нагрузке контексты (Bidding → Event Collector/Statistics → Campaign → Finance/Analytics), остальное остаётся в монолите, который параллельно разделяется на модули.
4. **За 3 месяца** достаточно: вынести Bidding Service с данными в памяти и Redis, перевести запись событий на Kafka, снять аналитику с primary-БД на реплику, добавить HA для PostgreSQL, Edge Gateway и наблюдаемость. Это убирает БД с hot path и даёт запас до ~25 000 RPS.
5. **Через год** — полностью событийно-ориентированная микросервисная система в Kubernetes, в двух регионах (active-active для RTB), с Database per Service и SLA 99.9%.
