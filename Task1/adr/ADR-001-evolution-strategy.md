# ADR-001. Стратегия эволюции архитектуры: от монолита к микросервисам через Strangler Fig

- **Статус:** Принято
- **Дата:** 2026-11-15
- **Участники:** архитектор, тимлиды backend и DevOps, CTO
- **Связанные решения:** [ADR-002](ADR-002-bidding-service-first.md), [ADR-003](ADR-003-event-streaming-technology.md)

## Контекст

- AdScale — гибридный монолит (C++ / Go / Python / Node.js) с одной PostgreSQL, без кеша, очередей, контейнеризации и CI/CD. Архитектура не задокументирована.
- Система уже на пределе: 15 000 RPS в пике, P95 110–120 мс при требовании ≤ 100 мс.
- Через 3 месяца нужно подключить DSP: трафик +20% (≥ 18 000 RPS), SLA ≤ 80 мс, штрафы за latency и downtime. Через год — 50 000 RPS, мультирегион, SLA 99.9%.
- Ограничения: бюджет ограничен, полное переписывание невозможно, нужна непрерывность бизнеса, команда 35 человек без SRE.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Оставить монолит, оптимизировать (кеш, индексы, вертикальное масштабирование БД) | Быстро, дёшево, минимум рисков | Не решает связность через общую БД, нет независимого масштабирования hot path, не достигает 50 000 RPS и мультирегиона |
| B. Переписать всё на микросервисы (Big Bang) | Целевая архитектура «сразу» | Не укладывается в 3 месяца; высокий риск; команда не готова эксплуатировать десятки сервисов; неизвестные границы → распределённый монолит |
| C. Модульный монолит | Снижает связность кода, дешёво | Один деплой и один процесс: нет изоляции отказов и независимого масштабирования аукциона |
| **D. Strangler Fig + модуляризация остатка** | Первый результат через 6–8 недель; трафик переключается постепенно с откатом через роутинг; масштабируем только то, что нужно | Период сосуществования двух систем; нужна синхронизация данных (CDC); временное усложнение инфраструктуры |

## Решение

Принимаем **вариант D**:

1. Ставим **Edge Gateway (Envoy)** перед монолитом — это «фасад» Strangler Fig, через который трафик переключается на новые сервисы по партнёру, проценту или маршруту.
2. Выносим сервисы **в порядке убывания бизнес-риска и нагрузки**:
   1. Bidding Service (Ad Server + Auction Engine) — SLA перед DSP;
   2. Event Collector + Statistics через Kafka — снятие write-нагрузки с БД;
   3. Campaign Service — источник конфигурации для аукциона;
   4. Budget & Pacing, User Profile;
   5. Finance Service и Analytics Service;
   6. вывод из эксплуатации остатка монолита.
3. Остаток монолита **разделяем на модули** с явными интерфейсами и собственными схемами БД, запрещаем межмодульные JOIN — это готовит следующие шаги выноса.
4. Данные между монолитом и новыми сервисами синхронизируются через **CDC (Debezium) и Transactional Outbox → Kafka**. Новые сервисы не читают таблицы монолита напрямую.
5. Каждый вынос проходит одинаковый цикл: **shadow traffic → canary (1/10/50/100%) → удаление кода из монолита**.
6. Обязательный фундамент до первого выноса: наблюдаемость (OpenTelemetry, Prometheus), нагрузочный стенд, контейнеризация, CI/CD.

## Последствия

**Положительные**
- Цель через 3 месяца достижима: самый критичный контекст выносится первым.
- Риск для бизнеса минимален: в любой момент трафик возвращается на монолит.
- Команда наращивает компетенции в эксплуатации распределённой системы постепенно.
- Затраты распределены по году и привязаны к измеримым результатам.

**Отрицательные и риски**
- Временное дублирование логики (старый и новый аукцион) → нужна сверка ответов в shadow-режиме.
- Eventual consistency между монолитом и новыми сервисами (задержка CDC — секунды) → для бюджетов используется механизм lease с ограничением перерасхода.
- Рост числа компонентов (Kafka, Redis, Debezium, Envoy) при отсутствии SRE → используем managed-сервисы, где это окупается, назначаем ответственных за платформу в DevOps-команде, вводим runbook'и.
- «Вечная миграция»: риск, что монолит не будет выключен → каждая фаза заканчивается удалением кода из монолита, прогресс отслеживается метрикой «доля трафика/функций в новой архитектуре».

## Критерии пересмотра

Решение пересматривается, если через 8 недель Bidding Service не принимает canary-трафик или если стоимость синхронизации данных превышает выгоду от выноса конкретного контекста.
