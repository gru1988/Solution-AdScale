# AS-IS: анализ текущей архитектуры AdScale

Диаграмма: [diagrams/as-is-c4-container.puml](diagrams/as-is-c4-container.puml)

## 1. Краткое описание текущей системы

AdScale — гибридный монолит (C++ / Go / Python / Node.js), развёрнутый вручную в одном production-кластере без контейнеризации. Все модули работают с **одним инстансом PostgreSQL**. Кеша и очередей нет.

| Компонент | Технология | Роль | Работа с БД | Критичность |
|---|---|---|---|---|
| Ad Server | C++, Go | приём bid request, идентификация пользователя, подбор кандидатов | синхронное чтение таргетинга | hot path, latency-critical |
| Auction Engine | C++ | бизнес-правила, взвешивание ставок, выбор победителя | синхронное чтение ставок и кампаний | hot path, самый чувствительный |
| Delivery Service | Node.js | HTML/JS-разметка и HTTP-ответ | — (вызывает Statistics) | hot path |
| Statistics Service | Python | запись показов и кликов | прямая запись без буферизации | высокая write-нагрузка |
| Financial Service | Go | списания, счета, балансы | транзакции | денежная целостность |
| Analytics Service | Python | отчёты | тяжёлые SQL на production | некритичный, но мешает всем |
| Advertiser Dashboard | Node.js + JS | UI рекламодателя | CRUD | бизнес-критичный, не latency-critical |

Внешние системы: DSP-партнёры (OpenRTB поверх HTTPS), платёжный шлюз (REST), пользователи сайтов и приложений (показы и клики), рекламодатели (UI).

## 2. Путь запроса на ставку и оценка бюджета времени отклика

Путь bid request сейчас целиком синхронный:

```
DSP → Ad Server → [PostgreSQL: таргетинг] → Auction Engine → [PostgreSQL: ставки/кампании]
    → Delivery Service → Statistics Service → [PostgreSQL: INSERT события] → ответ DSP
```

Оценка вклада каждого шага в P95 (по типичным значениям для подобных систем, т.к. трассировки нет — это первая проблема):

| Шаг | Оценка P95, мс | Комментарий |
|---|---|---|
| Сеть + TLS до AdScale | 8–12 | вне нашего контроля, зависит от DSP |
| Ad Server: парсинг, идентификация пользователя | 3–5 | |
| Ad Server: чтение таргетинга из PostgreSQL | 15–25 | растёт при конкуренции с записью и аналитикой |
| Auction Engine: чтение ставок/кампаний из PostgreSQL | 25–35 | несколько синхронных запросов на аукцион |
| Auction Engine: вычисления | 5–8 | собственно бизнес-логика быстрая |
| Delivery Service: разметка | 5–8 | Node.js, межъязыковой вызов внутри монолита |
| Statistics Service: синхронный INSERT | 10–20 | запись в hot path, блокировки и WAL |
| Сериализация ответа + сеть | 5–8 | |
| **Итого** | **≈ 80–120** | совпадает с наблюдаемыми 110–120 мс |

**Вывод:** около 50–80 мс из 110–120 мс — это обращения к PostgreSQL. Сама бизнес-логика аукциона занимает единицы миллисекунд. Значит, оптимизировать код аукциона бесполезно, пока БД остаётся на hot path. Нужно убрать синхронные обращения к БД из пути запроса.

## 3. Узкие места (bottlenecks)

| # | Узкое место | Механизм деградации | Влияние на latency |
|---|---|---|---|
| B1 | **Единая PostgreSQL** | OLTP-чтения аукциона, поток INSERT событий, финансовые транзакции и аналитика делят CPU, I/O, buffer cache, пул соединений и WAL | Основной источник хвостовых задержек (P95/P99) |
| B2 | **Синхронные чтения в Auction Engine и Ad Server** | Каждый аукцион делает несколько round-trip в БД, данные кампаний почти не меняются, но читаются каждый раз | +40–60 мс на запрос |
| B3 | **Statistics Service пишет напрямую** | При 15 000 RPS это порядка 10–20 тыс. INSERT/с (лог ставок, показы, клики), без batch-вставок; растут WAL, autovacuum, блокировки индексов | Запись в hot path + замедление всех остальных запросов |
| B4 | **Analytics Service на production-БД** | Тяжёлые агрегаты, full scan и сортировки вытесняют горячие данные из shared buffers, держат снапшоты, мешают vacuum | Пики latency во время построения отчётов |
| B5 | **Нет кеша** | Повторное чтение неизменяемых в рамках минут данных (кампании, креативы, таргетинг) | Лишние запросы в БД |
| B6 | **Ad Server и Auction Engine нельзя масштабировать отдельно** | Чтобы добавить мощности аукциону, надо поднять весь монолит, включая UI и аналитику | Нет горизонтального масштабирования hot path |
| B7 | **Межъязыковые вызовы внутри монолита** | C++ → Node.js → Python в одном запросе, сериализация между рантаймами | +5–10 мс, сложность профилирования |

## 4. Точки отказа (SPOF)

| # | Точка отказа | Последствие | Вероятность |
|---|---|---|---|
| F1 | **PostgreSQL, один инстанс, без HA** | Полная остановка: ни аукциона, ни UI, ни финансов. Потеря данных до последнего бэкапа | средняя, ущерб критичный |
| F2 | **Монолит как один процесс/деплой** | Утечка памяти в аналитике или ошибка в UI роняет аукцион. Любой релиз — риск для hot path | высокая |
| F3 | **Один production-кластер, один регион** | Авария ЦОД = полный простой, штрафы DSP | низкая, ущерб критичный |
| F4 | **Ручной деплой** | Долгий и рискованный откат, человеческий фактор | высокая |
| F5 | **Нет изоляции потоков (bulkhead)** | Всплеск кликов или тяжёлый отчёт исчерпывает пул соединений к БД, аукцион получает тайм-ауты | высокая в часы пик |
| F6 | **Нет защиты от перегрузки** | Нет rate limiting, circuit breaker, load shedding: при росте трафика система деградирует целиком, а не отбрасывает лишнее | высокая при +20% трафика |

## 5. Архитектурные проблемы, препятствующие масштабированию

1. **Общая модель данных и общая БД** — сильная связность по данным между всеми модулями. Нельзя ни масштабировать, ни выделить модуль, не распутав схему.
2. **Смешение критичных и некритичных потоков** — аукцион (≤ 100 мс), запись событий (eventual consistency допустима), финансы (строгая консистентность), аналитика (минуты допустимы) работают на одних ресурсах.
3. **Синхронность там, где она не нужна** — запись статистики и формирование счетов не обязаны завершаться до отправки ответа DSP.
4. **Отсутствие наблюдаемости** — нет распределённой трассировки, метрик по перцентилям на каждом шаге, SLO и алертов. Нельзя доказать DSP соблюдение SLA и быстро найти причину деградации.
5. **Отсутствие инфраструктурной базы** — без контейнеров, CI/CD и оркестрации невозможно автоматическое горизонтальное масштабирование и безопасные релизы (canary, blue-green).
6. **Нет документации и выделенных ролей (SRE, аналитик)** — знания об архитектуре сосредоточены у отдельных разработчиков, что повышает риск любой миграции.

## 6. Влияние на бизнес при росте нагрузки

- При росте трафика до 18 000 RPS (+20%) в той же архитектуре нагрузка на PostgreSQL растёт как минимум линейно (чтения + записи), а latency — нелинейно из-за конкуренции за блокировки и пул соединений. Ожидаемый P95 — **150 мс и выше**.
- Новый DSP требует **≤ 80 мс** и штрафует за деградацию и простои. При текущих 110–120 мс SLA нарушается уже сегодня.
- Ответы позже тайм-аута DSP фактически равны no-bid: AdScale **проигрывает аукционы** и теряет выручку даже без явных ошибок.
- Деградация затрагивает и текущих клиентов, так как ресурсы общие.

## 7. Итоговая карта рисков

| Риск | Вероятность | Ущерб | Приоритет | Чем закрываем (см. TO-BE) |
|---|---|---|---|---|
| Нарушение SLA 80 мс перед новым DSP | высокая | штрафы, потеря партнёра | **P0** | Bidding Service без БД на hot path, кеш, тайм-аут-бюджет |
| Падение PostgreSQL | средняя | полный простой | **P0** | Patroni HA, реплики, PITR |
| Перегрузка БД записью событий | высокая | рост latency всех потоков | **P0** | Kafka + batch-запись в ClickHouse |
| Аналитика блокирует OLTP | высокая | пики latency | **P1** | read replica → ClickHouse |
| Каскадные отказы при перегрузке | высокая | деградация целиком | **P1** | rate limiting, circuit breaker, load shedding |
| Рискованные ручные релизы | высокая | простои | **P1** | Docker, CI/CD, canary |
| Авария единственного ЦОД | низкая | многочасовой простой | **P2** | мультирегион (через год) |
